# AI 半小时写完 9 章重构方案？真正值钱的是后面那几次追问

> **TL;DR**
> 上一篇《[干了十几年 Java 的老登，我都让 AI 接管了哪些日常工作？](/blog/java-veteran-ai-workflow-in-depth/)》里，我说一份 9 章的重构方案是 AI 半小时写出来的。不少人私信要 Prompt。
>
> 回看当时的对话记录，**初稿确实只花了半小时，但方案真正敢上生产，靠的是之后两周里的几次追问**。本文复盘这个过程，最后附一份可直接复用的输入模板和审查清单。

---

## 一、背景：一次 4.9 秒的打分，有 4.5 秒在等自己

特征查询服务里有 16 个模型算子。它们为了凑齐模型入参，会在执行中**再调一次自己的 `query()`**：

```java
FeatureResponse resp = SpringContextHolder.getBean(IFeatureQueryService.class).query(innerRequest);
```

单次打分约 4.9s，其中内层嵌套占 4.5s。而且内外层共用同一个 IO 线程池：外层线程阻塞等待内层，内层任务排在队尾，形成**同池饥饿**。

改造方向是：**外层请求一进来，就把内层查询并发预拉取好，算子直接取用结果。** 难点不在代码本身，而在三件事：怎么证明打分一个都不变、用线上配置的沙箱怎么不碰生产、怎么灰度和回滚。

---

## 二、给 AI 的输入：只有四样，但一样不能缺

| 输入 | 我给了什么 | 为什么 |
| :--- | :--- | :--- |
| **背景** | 性能分析文档、数据流转文档的链接，代码路径 | 让 AI 自己去读，比口述准确 |
| **方向** | 只改嵌套；新包部署到沙箱，用 tcpcopy 从线上倒流量，重点看打分是否一致 | 选哪条路是决策，由人来定 |
| **红线** | 外数调用涉及计费；沙箱只处理模型分请求，其他请求直接返回 | AI 不知道哪个接口一调就要花钱 |
| **范围** | RPC 字段合并、线程池调参都不做 | 不划范围，它会把能想到的优化全塞进来 |

最后加一句：**“重新完整仔细评估下。”** 意思是让它先判断这个方向站不站得住，而不是顺着我的思路往下写。

半小时后，AI 交出了 9 章初稿：背景范围、改动总览、核心机制、执行流程、灰度配置、沙箱保护、对比口径、还原回滚、风险清单。**我审稿的第一个标准是：每一章能不能对应评审会上一定会被问到的一个问题。对应不上的就删掉。**

---

## 三、人当审判官：5 次关键追问

### 1. “tcpcopy 拷过去的流量，会不会有其他接口写线上？”

**这是整份方案里最重要的一问。** 初稿只在 `query()` 入口做了拦截，但同一个进程里还有 Kafka 消费者、消息订阅、短信告警，以及其他对外接口。沙箱用的是线上配置，这些组件一启动，就会**在线上的消费组里抢分区、往线上存储里写数据**。

AI 把所有入口和后台组件挨个排查了一遍，补出了一张保护表：

| 入口 / 组件 | 不处理的后果 | 沙箱处理 |
| :--- | :--- | :--- |
| 主查询 | 外数实时调渠道，产生计费 | 只放行模型特征，全部请求强制征信缓存，不回写变量库 |
| 试算接口、批量生成 | 计费、写线上 Mongo | 直接返回 |
| Kafka 消费 / 消息订阅 | 分走线上分区和消息，写线上存储 | 不启动 |
| 短信告警 | 告警发到值班手机上 | 只打日志 |

另外还有两道兜底：**取不到环境标识就直接拒绝服务**，以及一个可以一键熔断的流量总开关。

> AI 会把你点名的入口改得很完美，但不会主动想“这个进程里还有谁在干活”。这个问题要人来问。

### 2. “预拉取和直接在外层拍扁平，有啥区别？用两个具体算子举例”

拍扁平，就是在外层把内层要用的变量一次拉完，看起来更简单。**“用具体的 X 举例”是我最常用的追问**：不让它举例，它只讲原则；一旦要求举例，它就得去读代码，问题自然就暴露了：

- **参数别名**：内层参数按 `aliasCode` 重命名过（外层叫 `idNo`，内层叫 `idCardNo`），16 个算子有 16 套映射规则；
- **AES 解密**：外层只带密文时，拍扁平后内层拿到的是空明文，**接口不报错，入参静默变成 -99**；
- **缓存 key 错位**：缓存 key 按参数名取值，取不到的参数直接跳过。严重时 key 里不再包含区分用户的字段，**A 用户命中 B 用户的缓存，数据就串了**。

AI 最后总结的一句话，我原样写进了文档：**拍扁平改的是“用什么请求去算”，预拉取改的只是“什么时候算、算几次”。**

### 3. “这一行改了参数，预拉取没执行到，不就不一样了吗？”

这是我自己读代码时找出来的茬。AI 的回答是：探测阶段执行的就是算子自己的 `_prepare`，这段改参数的逻辑同样会跑；就算哪里真的对不上，还有签名校验兜底，签名不一致就降级回老链路。

> AI 说“已保证一致”的时候，要挑一个具体的代码位置去反驳它。这一步没法外包给 AI。

### 4. “灰度太复杂了，简化下”

初稿里有好几层开关。最后只留下 4 个字段：

```json
{ "globalSwitch": "CLOSED", "graySceneIds": [], "grayPercent": 0, "sandboxModelDataSourceIds": [] }
```

上线流程是：总开关关闭发布 → 按场景灰度，新老链路双跑比对 → 按比例灰度放量 → 出问题一键关闭总开关回滚，不用发版。AI 在这里补了一个好细节：**已验证的场景要移出白名单**，否则这些场景会一直双跑，外部调用量翻倍。

### 5. 我拍错的一板：“CacheRefresh 关了吧”

当时我觉得沙箱不需要本地缓存刷新，就让 AI 关掉了。一周后对比数据，出现了一批 `modelKey` 对不上的请求。原因是拷贝期间有人在线上改了配置，**线上节点刷新了，沙箱没刷新**。后来又加了回来：这个订阅是广播模式，只读不写，订阅它反而能减少对比噪音。

> 让 AI 把每个决策的**理由**写进文档。以后被数据打脸时，能很快找到当初是基于哪个假设拍的板。

## 四、用数据拍板：沙箱能不能放开全部模型？

一开始只敢放开一个模型。原因是它的内层本来就强制走征信缓存，不会产生计费。其他模型放开以后会不会真实调用渠道？我让 AI 去统计，**口径要先定死**：

- 每个分组抽一台机器，统计各模型的调用量和内层外数请求量；
- 按流水号逐条关联征信服务的计费账单，取出缓存命中和渠道调用情况（关联率 98.4%）；
- 每一行都必须满足 **`外数请求 = 命中缓存 + 真实调渠道 + 无账单`**。

统计出来的结论很清楚：其余模型的缓存命中率在 45%~99% 之间，沙箱和线上并发请求时会额外调用渠道。于是方案改为：**沙箱对全部请求统一强制征信缓存**。16 个模型全部放开，额外计费为 0。

> 任何“应该没问题吧”的地方，都换成“让 AI 统计一下”。但校验口径要人来给，否则它会交回一堆对不上账的数字。

## 五、从单沙箱到双沙箱：把环境噪音和真实改动分开

单台沙箱和线上对比时，不一致的结果里混着两种原因：强制缓存、缓存命中时序这类环境差异，和真正的改动差异。**一旦对不上，就分不清是 bug 还是噪音。**

我提出加一台沙箱当对照组：

![双沙箱流量镜像与三方比对架构图](/java-veteran-ai-workflow/01_dual_sandbox_arch.png)

| 节点 | 链路 | 作用 |
| :--- | :--- | :--- |
| 线上 | 老链路 | 基准 |
| 沙箱 A（`SANDBOX_MODEL_FLOW=A_ONLY_CACHE`） | 老链路 + 强制缓存 | 线上 vs A = 环境噪音 |
| 沙箱 B（`SANDBOX_MODEL_FLOW=B_NEW`） | 新链路 + 强制缓存 | A vs B = 本次改造 |

两台沙箱用**同一个包，靠环境变量切换**。这一轮 AI 补了两个真坑：

- 两条 tcpcopy 任务要各自指向一个 IP。否则流量会被负载均衡分到两边，A 和 B 的流水号对不上；
- 在实现开关时，它发现沙箱的特征过滤会把**老链路的内层请求也过滤掉**，导致 A 的结果全错。如果没发现这个问题，A 的对比数据会全部作废。

其中一组对照的真实结果：1641 个请求、7069 个模型分。其中三方一致 5486 个，A=B≠线上（环境噪音）1579 个，**三方都不同的只有 3 个**。纯模型请求的耗时中位数，B 比 A 提升 11.9%。

## 六、拿去就能用

### 输入模板

```text
【背景】问题分析文档：<链接>；代码：<路径>，重点模块：<包名>
【方向】本次只解决 <一个问题>，做法是 <一句话>。验证方式：<怎么证明结果不变>
【红线】<绝对不能发生的事，如：不能产生计费 / 不能写线上存储>
【范围】做：<A>；不做：<B>、<C>
请先重新完整仔细地评估方向是否可行，再输出方案。
每个决策写明理由，每个数字写明依据（来自哪段代码或哪份统计）。
```

### 审查清单

- [ ] 每一章都能对应评审时的一个问题吗？有没有夹带顺手的优化？
- [ ] “为什么不用更简单的方案？”让 AI 拿真实代码举出反例
- [ ] 挑一个具体代码位置，反驳“已保证一致”
- [ ] 魔法数字（超时、线程数）是从现有代码推出来的吗？
- [ ] **同一个进程里还有谁在干活？** 哪些调用会计费、会写数据？
- [ ] 取不到环境标识时，默认行为安全吗？有一键熔断吗？
- [ ] “不一致”怎么定义？有对照组来区分噪音吗？
- [ ] 回滚要不要发版？临时改动上线前怎么还原？

## 结语

这份方案的文字几乎都是 AI 写的，但几个关键转折点（沙箱保护补全、拍扁平之争、全量强制缓存、双沙箱对照）都是追问出来的。AI 也不只是打字：老链路被过滤打坏、tcpcopy 被负载均衡分流这两个坑，是它在读代码时自己挖出来的。

所以上一篇说的“人只做审判官”，更准确的说法是：**人负责问出 AI 想不到的问题。**
