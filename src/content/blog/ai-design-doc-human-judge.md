# AI 半小时写完 9 章重构方案？真正值钱的是后面那 9 次追问

> **TL;DR**
> 上一篇《[干了十几年 Java 的老登，我都让 AI 接管了哪些日常工作？](/blog/java-veteran-ai-workflow-in-depth/)》里，我说一份 9 章的重构方案是 AI 半小时写出来的。不少人私信要 Prompt。
>
> 这篇把老底翻出来。我回看了当时的全部对话记录，**AI 的初稿确实只花了半小时，但方案真正能拿去评审、敢在生产上灰度，靠的是之后两周里我对它的 9 次追问**：有的追问让它补上了漏掉的生产风险，有的让它砍掉了过度设计，还有一次是我自己拍错了板，后来又改了回来。
>
> 本文按时间线复盘：**怎么喂输入 → 初稿长什么样 → 人怎么审 → 怎么用数据拍板 → 方案怎么演进到“双沙箱三方对比”**，最后给出可直接复用的输入模板和审查清单。

---

## 一、先交代背景：一个 4.9 秒的打分，4.5 秒在等自己

我们有一个特征查询服务，Java 写的，跑了很多年。里面有 16 个“模型算子”，负责准备入参、调用模型平台打分。问题出在它们准备入参的方式上：

```java
// 模型算子内部，为了凑齐模型入参，再调一次自己的 query()
FeatureResponse resp = SpringContextHolder.getBean(IFeatureQueryService.class).query(innerRequest);
```

也就是**嵌套查询**：外层请求执行到模型算子时，算子才去发起一次内层查询，拉几千个变量，拉完再调模型打分。线上抽样的数据很难看：

- 单次打分约 **4.9s**，其中内层嵌套拉取约 **4.5s**，占 91.5%；
- 内外层共用同一个 IO 线程池：外层线程阻塞等内层，内层任务排在同一个池的队尾，**同池饥饿**。跑批高峰时整个分组都被拖慢。

改造方向不复杂：**别等算子执行到了才去拉，外层请求一进来就把内层查询并发预拉取，算子直接取结果。**

难的是三件事：

1. **怎么证明改完以后打分一个都不变？** 这是风控模型分，错一个分就是线上事故；
2. **验证环境怎么搭？** 想拿真实流量验证，沙箱就得用线上配置，而用线上配置的沙箱，随便一个写操作都会污染生产；
3. **怎么上线、怎么回滚？**

这三件事落到文档上就是几十页的细节。我决定只自己定方向，细节全部交给 AI 写。

## 二、第一步：只给 AI 四样东西

很多人以为“让 AI 写方案”就是丢一句“帮我写个重构方案”。那样出来的东西基本是正确的废话。

我给的输入只有四样，但每一样都不能缺：

| 输入 | 我实际给了什么 | 为什么必须给 |
| :--- | :--- | :--- |
| **① 背景材料** | 之前的《跑批任务性能问题分析》文档，以及数据流转、表关系文档的链接；代码仓库路径 | AI 不知道你的系统长什么样，让它自己读，比你口述准确 |
| **② 方向** | “只改嵌套这一个问题，即模型分查询机制优化。新包部署到沙箱，从线上用 tcpcopy 倒流量过去，重点关注打分结果是否一致” | 方向由人定。AI 能列出 5 种方案，但选哪种要看团队能力、上线窗口和风险偏好，它判断不了 |
| **③ 红线** | “变量服务里涉及外数调用的计费和缓存问题，本次只影响模型分逻辑，所以沙箱只处理模型分相关请求，非模型分请求直接返回” | 红线是 AI 最不可能自己想到的东西。它不知道哪个接口一调就要付钱 |
| **④ 范围** | 明确“只做去嵌套”，同下游 RPC 字段合并、线程池调参这几项不做 | 不给范围，AI 会把它能想到的优化全塞进来 |

原话基本就是这么口语化的一段，最后加一句：

> **“重新完整仔细评估下。”**

这句话很重要，它告诉 AI：不要只顺着我的思路往下写，先评估这个方向本身站不站得住。

> **经验**：背景材料给文档链接和代码路径，让 AI 自己去读；方向、红线、范围这三样，由人用大白话写死。前者是信息搬运，后者是决策，分开给。

## 三、第二步：AI 交出的 9 章骨架

半小时左右，AI 交出了第一版完整文档。经过后面的打磨，最终定稿是下面这个结构：

| 章节 | 回答评审时的哪个问题 |
| :--- | :--- |
| 〇、线上调用统计 | 各分组调了哪些模型、调了多少次、多少外数真实调了渠道？（后补，见第五节） |
| 摘要 | 改了什么、怎么保证一致、怎么验证、怎么上线，每条一句话 |
| 一、背景与范围 | 为什么改、做什么、**不做什么** |
| 二、改动总览 | 新增哪些类、修改哪些类，每处改动一句话 |
| 三、核心机制 | 预拉取怎么保证和老链路**逐字等价**？ |
| 四、执行流程 | 改造前后的调用链对比、超时规则、线程占用 |
| 五、灰度配置 | 配置中心怎么配、上线 SOP、怎么一键回滚 |
| 六、沙箱部署与 tcpcopy 验证 | 沙箱用线上配置，**怎么保证不碰生产**？ |
| 七、日志与对比 | 用什么日志对比，**什么算真正的不一致**，哪些是噪音 |
| 八、上线前还原与回滚 | 临时改动怎么还原，线上和沙箱各自怎么回滚 |
| 九、风险与注意事项 | 已知风险、待确认事项、应对措施 |

注意右边那一列：**每一章都对应评审会上一定会被问到的一个问题。** 这是我判断 AI 初稿合不合格的第一个标准。如果某一章答不出一个具体问题，它就是凑字数，删掉。

AI 写这种骨架非常快，也非常全。但初稿里的细节，有不少经不起追问。

## 四、第三步：人当审判官——9 次追问实录

下面这 9 次追问，都是从当时的对话记录里原样摘出来的。每一条我都写了：**我问了什么、为什么问、方案因此改了什么。**

### 追问 1：“灰度控制太复杂了，简化下”

初稿的灰度配置有好几层开关，还有一个独立的“是否比对数据”开关，看着很周全。

我的判断是：**配置项越多，线上出事时越没人敢动。** 于是直接给了简化规则：

> “沙箱直接跑新逻辑，用日志和线上节点对比；线上可以控制总开关，可以按场景灰度并对比数据，没问题就直接按比例灰度，不再比对数据。”

最终的配置只剩 4 个字段：

```json
{
  "globalSwitch": "CLOSED",
  "graySceneIds": [],
  "grayPercent": 0,
  "sandboxModelDataSourceIds": []
}
```

| 阶段 | 配置 | 行为 |
| :--- | :--- | :--- |
| 发布 | `CLOSED` | 与改造前完全一致 |
| 场景灰度 | `OPEN` + 1~2 个场景 | 新老链路都跑并比对，返回新结果，新链路异常用老结果兜底 |
| 比例灰度 | 已验证场景**移出**白名单，`grayPercent` 10 → 50 → 100 | 只跑新链路，不再比对 |
| 回滚 | `CLOSED` | 秒级回到老链路，不用发版 |

AI 在定稿时自己补了一条很关键的提醒：**已验证的场景一定要移出 `graySceneIds`，否则这些场景会一直新老双跑，外部调用量翻倍。** 这种细节它补得很好。

> **审查要点**：AI 倾向于“把所有可能都配置化”。人要问：出事的时候，值班同学能在 30 秒内看懂这份配置吗？

### 追问 2：“等待预拉取的超时时间是啥，这个正确吗？”

预拉取要等多久才放弃？这个值定得不对，要么白白占着线程，要么在主 job 还没超时的时候就提前放弃了。我追问之后，AI 回头核对了调度器的源码，把规则和依据都写进了文档，和主 job 完全一致：

```
截止时间 = 提交预拉取时刻 + effectiveOutTime(外层 readTimeOut)
effectiveOutTime：readTimeOut <= 0 → 10000ms；否则 min(readTimeOut, 15000ms)
```

理由也写进了文档：主 job 超时以后，外层请求已经返回，再等预拉取也没有意义。**超时值要从现有代码里推出来，不能凭感觉拍一个数。**

> **审查要点**：方案里出现的每个魔法数字（超时、线程数、重试次数），都要追问一句“依据是什么”。AI 给的数经常是合理的，但不一定和你系统现有的规则一致。

### 追问 3：“tcpcopy 拷到沙箱的流量，会不会有其他接口改了缓存或数据库，影响线上？”

**这是整个方案里最重要的一次追问。**

当时的初稿只在主查询入口 `query()` 做了沙箱拦截。但这个服务对外暴露的不止一个接口，进程里还有 Kafka 消费者、消息订阅、短信告警、定时任务。沙箱用的是线上配置，**这些组件一启动，就是在线上的消费组里抢分区、往线上存储里写数据。**

我的原话是：

> “我现在只改了 query，其他方式是不是应该注释掉直接返回？”

AI 把整个服务的所有入口和后台组件挨个排查了一遍，产出了这张保护措施表。判断条件统一为“`CLOUD_ENV=SandBox` 或取不到环境标识”：

| 入口 / 组件 | 不处理的后果 | 沙箱处理方式 |
| :--- | :--- | :--- |
| 主查询 `query()` | 外层外数实时调渠道，产生计费 | 只放行模型相关特征，其余剔除；**全部请求强制征信缓存**；**跳过变量库回写** |
| 试算接口 | 同上 | 直接返回空 |
| 身份证批量生成 | 写线上 Mongo | 直接返回 |
| Kafka 消费者 | 消费组来自线上配置，会分走线上分区，并写线上 KV 存储 | 不启动 |
| 消息队列订阅 | clientId 与线上相同，会分走线上消息 | 不启动 |
| 短信告警 | 沙箱告警发到值班手机 | 只打日志 |
| 本地缓存刷新订阅 | 见追问 6 | **照常订阅**（广播模式，只读） |
| 只读查询接口 | 无副作用 | 不处理 |

外加两道兜底：

- **环境标识兜底**：取不到环境变量时直接拒绝服务（`SYSTEM_ERROR`），宁可不可用，也不能把沙箱误当成线上；
- **流量总开关**：配置中心一个 key，置 `0` 后沙箱对所有拷贝流量直接返回空，作为紧急熔断。

部署后还要检查启动日志，确认“不启动 Kafka 消费”“不启动消息监听”这几行都出现了，并且**不应该出现**“开始消费消息 topic”。

> **审查要点**：AI 会把你点名的那个入口改得很完美，但不会主动去想“这个进程里还有谁在干活”。**“同一个进程里还有哪些东西会产生副作用？”** 这个问题要由人来问。

### 追问 4：“并发预拉取和直接在外层把变量拉平，有啥区别？”

方案的核心机制是：外层先**探测**每个模型算子要发的内层请求，再**并发预拉取**，算子执行时**按签名匹配**取用结果。

一个更直观的方案是**拍扁平**：在外层把内层要的变量直接并到外层请求里，一次拉完，算子再从里面挑参数组装。看起来更简单、更快。

我问 AI 两者的区别，又追了一句：

> “能举例说明吗？用具体的两个算子。”

**“用具体的 X 举例”是我最常用的追问方式。** 不要求举例时，AI 只给原则；一要求举例，它就得去读代码，问题自然暴露出来。它挑了两个算子：

**例 1：参数别名。** 算子按 `aliasCode` 重命名参数，外层叫 `idNo`，内层叫 `idCardNo`；某些别名（`acv17SceneId`）不进参数 map，只用来确定场景；还有一些参数既进 map 又决定 `orderNo`。16 个算子有 16 套规则，在外层重写一遍很难不漏。

**例 2：AES 解密。** 外层请求只带密文 `idCardNoAES` 时，算子内部会解密成明文再查。拍扁平后，内层变量拿到的是空明文，**接口不报错，只是大量入参变成 -99，分数静默变化**。

更致命的是**缓存语义**。变量库的缓存 key 是这样拼的：

```java
StringBuilder keyBuilder = new StringBuilder(featureId).append("_").append(version).append("_");
for (Param param : paramGroup.getParams()) {
    if (params.get(param.getCode()) == null) { continue; }   // 取不到就跳过
    keyBuilder.append(params.get(param.getCode())).append("_");
}
```

拍扁平以后，按内层参数名在外层 params 里取不到值，这个参数就被**跳过**。轻则 key 和历史缓存对不上，永远不命中；**重则 key 里不再包含区分用户的参数，所有人共用一个 key，A 的特征值被 B 命中，也就是串数据。** 此外，内层是特殊场景，会读另一列缓存、强制走征信缓存；拍扁平后这些标记全部失效，几十个外数变成实时调用，开始计费。

最后，AI 把两种方案的本质区别总结成一句话，我原封不动放进了文档：

> **拍扁平改的是“用什么请求去算”，本方案改的只是“什么时候算、算几次”。前者改变了缓存语义，后者没有。**

签名的设计也在这一轮里讲清楚了：

```
signature = sceneId | 排序后的 groupIds | 按 key 排序的 params JSON（保留 null）
```

签名覆盖了决定缓存行为的全部输入，所以它是一个**保守的等价判据**：签名相同，说明两次请求逐字相同，可以共用结果；签名不同，就不复用，算子降级回老链路自己查。**最坏的结果是丢一点性能，不会用错数据。**

> **审查要点**：凡是“为什么不用更简单的方案”这类问题，都让 AI 拿真实代码举反例。举不出来，说明简单方案也许就够了；举得出来，这些反例就是方案里最有说服力的部分。

### 追问 5：“这一行改了参数，外部预拉取没先执行这段，参数不就不一样了吗？”

这次是我自己读代码时发现的疑点。某个算子在发起内层查询之前，先执行了一段逻辑修改参数。外层预拉取并没有执行这段代码，那预拉取的请求和算子实际要发的请求，不就对不上了吗？

AI 的回答是：**探测阶段执行的就是算子自己的 `_prepare`**，所以这段修改参数的逻辑同样会执行。只是执行到真正发起查询那一步时，Resolver 发现自己处在探测上下文里，于是只记录请求、不发起查询。即使真有对不上的情况，签名校验也会兜底降级。

我对着代码又看了一遍，最后在对话里留了一句：“大概理解了，就是现在的代码嵌套比较深，而且写了很多特殊逻辑。”

> **审查要点**：AI 说“已经保证一致”，你要挑一个具体的代码位置去反驳它。**人审方案，不是看它写得顺不顺，而是拿代码去找茬。** 这一步没法外包。

### 追问 6：“CacheRefresh 关了吧，沙箱测试不需要”（我拍错了的一板）

这一条要老实交代：**这次是我错了。**

做沙箱保护时，我觉得本地缓存刷新订阅在沙箱里没用，就让 AI 把它关掉了。一周后对比数据，出现了一批莫名其妙的不一致：某个模型的请求体里 `modelKey` 变了。顺着查下去才明白：**拷贝期间有人在线上改了配置，线上节点刷新了本地缓存，沙箱没订阅，还在用旧配置。**

于是我又让 AI 把刷新逻辑加了回来。这次它把理由写得很清楚：消息是广播模式，每个实例各收一份全量消息，沙箱订阅不会抢线上的消息；刷新只读数据库，不写任何东西。**订阅反而是为了让沙箱和线上配置保持一致，减少对比噪音。**

> **审查要点**：人也会拍错板。所以方案里的每个决策，最好都让 AI 把**理由**写进文档，而不只是写结论。这样数据打脸时，你能很快定位到当初是基于哪个假设做的决定。

### 追问 7：“这些都不要了”

初稿里还有三个看起来很有价值的章节：同下游 RPC 字段合并、线程池参数纠偏与动态调参、另外 7 个非模型嵌套算子按同样方式接入。

我直接一句话删掉了。理由很简单：**一次只改一个变量，对比才有意义。** 三项一起上，线上分数一变，根本说不清是哪个改动引起的。

AI 很擅长扩写，但没有“这次只做这些”的克制。**范围由人砍。**

### 追问 8：“外层查询不会走外数吗？”

决定只在沙箱放行模型相关请求以后，我又问了一句：外层请求里本身也有外数特征，它们会不会调渠道？

这一问让 AI 把“沙箱特征过滤”的位置和范围理清楚了：外层外数特征在沙箱过滤阶段就被剔除，只保留模型相关变量；**而且无论 A 还是 B、外层还是内层，所有请求都强制征信缓存。** 我最后用一句话让它确认：

> “也就是沙箱不管 A 还是 B、内层还是外层，都只放行模型分相关特征的查询，并且强制缓存，不会查询外数，对吧？”

**用自己的话把结论复述一遍，让 AI 确认。** 这是我在每个关键节点都会做的动作。复述过程中卡住的地方，通常就是还没真正想明白的地方。

### 追问 9：“一开始没设计成扁平的，而是嵌套的，是设计缺陷吗？”

这个问题跟方案本身关系不大，我是想搞清楚历史。没有任何文档记录过当初的考虑，AI 是翻了最早的调度框架代码和提交历史推出来的：

- 调度框架给每个请求构建的执行图是固定两层：`Head → 数据源调用 → 计算 → Tail`。所有数据源调用并行，**框架里不存在“特征 A 依赖特征 B 的结果”这种边**；
- 模型分恰恰需要“先算出几百个特征，再拿去打分”。当年加模型算子时只有两条路：改调度框架去支持特征之间的依赖，或者在算子里再调一次 `query()`；
- 后者不用动框架，参数映射、缓存、强制缓存全部复用，建模同学在平台上配一个场景就能上线新模型。**在当时是合理的取舍。**

它的结论是：**嵌套本身是合理的设计，同步阻塞地执行嵌套才是缺陷。** 这次修的是后者，没有推翻前者。

这个答案没有改动方案里的任何一行，但在评审会上被问到“当初为什么这么设计”时，我能给出一个公允的说法，而不是简单一句“前人留下的坑”。它也顺带说明了这次改造的边界：要彻底去掉嵌套，就得改调度框架，那是另一个量级的重构。

## 五、第四步：用线上数据拍板，不靠感觉

方案写到一半，卡在一个决策上：**沙箱能不能放开全部 16 个模型？**

最开始我们只敢放开一个模型，因为它的内层是特殊场景，本来就强制走征信缓存，不会产生计费。其他模型是普通场景，放开后它们内层的外数会不会真实调渠道？会调多少次？

这个问题不能靠拍脑袋。我给 AI 提的要求是：

> “每个分组抽一台机器，统计每个模型昨天的调用量、调用外数量。后续我想看其他模型能不能像那个模型一样直接在沙箱打开，还是需要开强制缓存，要靠统计数据来判断，**所以统计要准确**。”

AI 做的事情，人工几乎没法做：

- 6 个分组各抽一台机器，从日志里统计每个模型算子的内层调用次数；
- 通过线程上的“流水号映射”找到内层 job，统计内层发给征信服务的外数请求数；
- 按征信流水号，**逐条关联征信服务 6 个节点上的计费账单**，取出“是否命中缓存”“是否强制缓存”“渠道是否成功”，整体关联率 98.4%；
- 关联不上账单的 6641 次请求，再逐条追到征信服务的调用日志，拆成 6 类原因，逐个核实是否计费；
- 每一行都满足校验等式：**`外数请求 = 命中缓存 + 真实调渠道 + 无账单合计`**。

最后得出的几个结论直接决定了方案：

1. 16 个模型里，线上真正在用的只有 6 个；
2. 除特殊场景外，其余 5 个在用模型的内层外数缓存命中率在 45%~99% 之间。**沙箱如果和线上同时请求，两边都没命中缓存，就会都去调渠道**，额外计费从几次到上千次不等；
3. 所以方案是：**沙箱对全部请求统一强制征信缓存**。这样一来，16 个模型可以全部放开，额外计费为 0。

> **经验**：方案里任何“我觉得应该没问题”的地方，都换成“让 AI 去统计一下”。AI 做穷举统计不嫌累，但你要给它**校验口径**（比如上面的校验等式），否则它可能交给你一堆对不上账的数字。

## 六、第五步：从单沙箱演进到“双沙箱三方对比”

第一版验证只有一台沙箱：线上跑老代码，沙箱跑新代码，按流水号对比。

跑了几天发现一个根本问题：**沙箱和线上的差异，不止“新代码 vs 老代码”这一项。** 沙箱强制走了缓存，线上没有；沙箱请求比线上晚几毫秒到达，缓存命中的时序也不一样。一旦出现不一致，分不清是改造引入的 bug，还是环境噪音。

我想到的办法是**再加一台沙箱作为对照组**，直接问 AI 是否可行：

> “准备把线上节点的流量同时拷贝到沙箱的两个节点。一套只改了强制使用缓存（保留本地缓存刷新），另一套在第一套基础上再加上本次优化。后续对比时同时对比线上和两套沙箱，看看这个方案是否可行。”

AI 给出“可行，建议这么做”的结论，同时补了几条我没想到的落地细节，每一条都是真坑：

1. **两台沙箱必须各收到一份全量流量。** 如果把拷贝目标配成一个有两个节点的沙箱集群，流量会被负载均衡分到两边，A 和 B 处理的流水号对不上，就没法比了。要配两条 tcpcopy 任务，各自指向一个 IP，上线后再用日志核对两台机器的流水号交集是否接近 100%；
2. **强制缓存标志不能只在外层设。** 内层 job 用的是新的上下文，外层设的标志传不进去，要在查询入口里对沙箱统一设置；
3. **A 和 B 之间也有时序噪音。** B 的预拉取比 A 的嵌套调用发起得早，更容易碰上“线上还没把结果写进缓存”的情况。A、B 不一致时，要按征信账单里的缓存命中情况分开统计；
4. **A 和 B 最好用同一个包，靠配置切换**，不要维护两套代码，否则时间一长，“B 等于 A 加本次改造”这个前提就不成立了。

第 4 条 AI 给的实现是在配置中心里按机器 IP 配置链路模式。我嫌 IP 一漂移就要改配置，改成了：

> “使用同一份代码，用系统环境变量（和控制是否沙箱类似，云平台可以自定义环境变量，部署时可以选择）控制沙箱启动的是 A 还是 B。”

**AI 在实现这个开关的时候，又挖出了一个藏得很深的问题**：沙箱的“只放行模型特征”过滤只对新链路的预拉取做了豁免；老链路里算子嵌套调用 `bean.query()` 时，内层请求会被当成外层请求再过滤一遍，内层变量全被剔除，模型拿不到入参。也就是说，**沙箱 A 如果直接切到老链路，结果会全是错的**；沙箱 B 里签名不匹配、降级回老链路的那部分请求也会受影响。修法是在嵌套调用前给当前线程打一个标记，查询入口读到标记就按内层查询处理。

如果没发现这个问题，A 的对比数据会全部作废，还会被误判成“老链路和线上对不上”。

![双沙箱流量镜像与三方比对架构图](/java-veteran-ai-workflow/01_dual_sandbox_arch.png)

最终方案：

| 节点 | 环境变量 | 链路 | 作用 |
| :--- | :--- | :--- | :--- |
| 线上 | — | 老链路，不强制缓存 | 基准 |
| 沙箱 A | `SANDBOX_MODEL_FLOW=A_ONLY_CACHE` | 老链路 + 强制缓存 | **对照组**：线上 vs A 的差异 = 环境噪音 |
| 沙箱 B | `SANDBOX_MODEL_FLOW=B_NEW` | 新链路 + 强制缓存 | **实验组**：A vs B 的差异 = 本次改造 |

判定规则也随之明确下来：**三方中任意两方相同就算一致，三方两两都不同才算真正的不一致。** 其中“A=B≠线上”属于沙箱强制缓存带来的环境差异，不算 bug。

**同一个包、一个环境变量切换**，保证了 A 和 B 除了被测改动以外完全一致。

后来这套对照组扩展到了 12 组。其中一组的真实数据：

| 指标 | 数值 |
| :--- | :--- |
| A、B 共同收到的请求 | 1641 |
| 模型分总数 | 7069 |
| 三方一致 | 5486 |
| A=B≠线上（环境噪音） | 1579 |
| 三方都不同（需要排查） | 3 |
| 请求级一致 | 1638 / 1641 |
| 纯模型请求耗时中位数（B 相对 A） | 提升 11.9% |

1579 条环境噪音被干净地隔离了出来，真正需要排查的只剩 3 条。后来顺着这类“三方都不同”的数据往下挖，还挖出了一个**老链路里本来就存在**的线程竞争 bug。这部分是下一篇的内容。

### 7.2 审查清单：人审 AI 方案时必问的问题

**范围与决策**

- [ ] 每一章能对应评审会上的一个具体问题吗？对应不上的删掉
- [ ] 有没有夹带“顺手优化”？一次只改一个变量
- [ ] 每个决策都写了理由吗？（以后被数据打脸时，用来定位当初的假设）

**正确性**

- [ ] “为什么不用更简单的方案？”让 AI 拿真实代码举反例
- [ ] 挑一个具体代码位置，反驳“已保证一致”的说法
- [ ] 每个魔法数字（超时、线程数、重试次数）是从现有代码推出来的吗？

**生产安全**（尤其是用线上配置的验证环境）

- [ ] 同一个进程里还有谁在干活？消费者、订阅、定时任务、告警、对外的其他接口
- [ ] 哪些调用会计费？命中缓存和不命中各会怎样？
- [ ] 哪些调用会写数据？写到哪里？
- [ ] 取不到环境标识时，默认行为是安全的吗？
- [ ] 有一键熔断开关吗？

**验证与上线**

- [ ] “不一致”的定义写清楚了吗？哪些是噪音、怎么排除？
- [ ] 有对照组吗？能把环境噪音和真实改动区分开吗？
- [ ] 回滚需要发版吗？多久能生效？
- [ ] 临时改动（例如沙箱配置）上线前怎么还原？写进清单了吗？

### 7.3 几个追问句式

| 场景 | 句式 |
| :--- | :--- |
| 让 AI 去读代码 | “能举例说明吗？用具体的两个 X。” |
| 质疑数字 | “这个值是啥？这个正确吗？” |
| 找副作用 | “除了这个入口，还有哪些地方会 <写数据/计费/发消息>？” |

| 砍范围 | “这些都不要了。” |
| 要数据 | “统计一下 ……，后续要靠数据判断，所以统计要准确。” |

## 八、复盘：这次人机分工到底是怎么分的

| | AI 做的 | 人做的 |
| :--- | :--- | :--- |
| 方案骨架 | 半小时出 9 章初稿 | 按“每章回答一个评审问题”删改 |
| 核心机制 | 读 16 个算子的代码，论证等价性，写反例 | 定方向；拿具体代码位置找茬 |
| 生产保护 | 排查所有入口和组件，产出保护措施表 | **提出“还有谁在干活”这个问题** |
| 灰度方案 | 写配置、SOP，补“已验证场景要移出白名单”这类细节 | 砍掉多余的开关 |
| 关键决策 | 跨两个服务逐条关联日志和账单，交出可校验的统计 | 提出要统计什么、用什么口径校验、据此拍板 |
| 验证方案 | 补全双沙箱的落地细节（流量分流、标志传递、时序噪音）；实现开关时挖出“老链路被沙箱过滤打坏”的问题 | 提出“加一台对照组”；把按 IP 配置改成环境变量切换 |
| 犯错与纠正 | 按新数据把刷新逻辑加回来，并写清理由 | 拍错过一次板，被数据纠正 |

回头看，**这份方案的文字几乎都是 AI 写的，但方案里最关键的几个转折点，都是由人的追问引出来的：** 沙箱保护补全、拍扁平和预拉取之争、全量强制缓存、双沙箱对照。反过来，AI 也不只是在打字：老链路被沙箱过滤打坏、tcpcopy 被负载均衡分流这类坑，是它在读代码、写实现的过程中自己挖出来的。

所以上一篇说的“人只做审判官”，准确地说应该是：**人负责提出 AI 想不到的问题。** 审判官不是在终点签个字就行，要在整个过程中不停地问“这样对吗”“还有呢”“为什么”。
